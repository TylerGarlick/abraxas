# VOLUME III: THE ORCHESTRATION LAYER
## Janus and the $N$-of-$M$ Consensus Protocol

---

### 3.1 The Orchestrator's Role

The Sovereign Architecture (Volume II) provides the defensive shell—Soter detects epistemic failure, Sovereign-Nexus records the reasoning path, and Sovereign-Anchor injects human truths. But these components are static guards. The system also needs a dynamic intelligence that decides *how* to approach each query, orchestrating the interplay between probabilistic generation and deterministic verification.

This role is fulfilled by **Janus**, named for the Roman god of transitions, gates, and duality. Janus is the cognitive orchestrator that transforms Abraxas from a collection of tools into what we term a **Sovereign Brain**.

Janus operates on four principles:
1. **Mode Control** — Dynamically switching between probabilistic (NOX) and deterministic (SOL) processing
2. **Sovereign Spawning** — Running $M$ independent reasoning paths to break the parametric bias loop
3. **Consensus Gating** — Only emitting output when a deterministic agreement threshold is reached
4. **Epistemic Sealing** — Stamping every output with a verifiable confidence label

### 3.2 The Sovereign Switch: NOX and SOL

Janus manages two fundamentally different states of cognitive operation:

#### 3.2.1 NOX Mode (Intuitive / Generative)

NOX is the default mode. It corresponds to standard LLM behavior: the model generates responses based on its training distribution, optimized for fluency and helpfulness. NOX is fast, creative, and useful for low-risk interactions—general conversation, creative writing, and queries where the user is asking for synthesis rather than verified facts.

**Characteristics of NOX:**
- **Nature:** Probabilistic. The model predicts the most likely next token.
- **Labeling:** Responses may carry simulated confidence markers, but these are generated by the same probabilistic mechanism and are not architecturally guaranteed.
- **Safety:** Guidelines are embedded in the system prompt—vulnerable to Constraint Leakage (Vol I §1.3.2).
- **Use Case:** Chat, creative tasks, low-risk queries, exploration.

#### 3.2.2 SOL Mode (Analytical / Deterministic)

SOL is the sovereign state. When Soter detects a risk ($T = 1$), or when the user explicitly requests verification, Janus executes an immediate **Sovereign Switch**:

1. The NOX flow is killed.
2. The partial probabilistic output is discarded.
3. The system transitions to SOL mode.
4. Grounding-Before-Generation is activated (Mnemosyne retrieves fragments).
5. The $M$-Lens consensus protocol is launched (see §3.3).

**Characteristics of SOL:**
- **Nature:** Deterministic. Every claim must be grounded in a retrieved fragment or a Genesis Block.
- **Labeling:** Responses carry the `[Sovereign Consensus: X/5]` seal, generated by code, not by the model.
- **Safety:** Constitutional rules are enforced by the Soter veto gate—not bypassable.
- **Use Case:** Factual claims, high-risk data, critical logic, adversarial queries.

#### 3.2.3 The Trigger Mechanism

The transition from NOX to SOL is governed by the Soter attention-sink tripwire ($\tau = 0.15$) described in Vol II §2.2. Additionally, users can force SOL mode with the `/sol` command, or configure specific risk thresholds to trigger automatic switching based on query content patterns.

The Sovereign Switch is irreversible within a single query. Once in SOL mode, the system cannot revert to probabilistic guessing. The entire response must be generated through the deterministic pipeline or returned as `[Sovereign Unknown]`.

### 3.3 Sovereign Spawning: The $M$-Lens Architecture

A fundamental failure mode of single-path LLM reasoning is the **parametric bias loop**. When a model generates a response, each new token is conditioned on the tokens it has already produced. If the model makes an early error, that error biases all subsequent tokens. The model effectively agrees with its own first mistake and builds a coherent argument on a false foundation.

Janus breaks this loop through **Sovereign Spawning**. In SOL mode, instead of a single reasoning path, Janus spawns $M$ independent paths (typically $M = 5$), each initialized with a unique **Epistemic Lens**—a distinct cognitive persona with a specific verification mandate:

| Lens | Mandate | System Prompt |
| :--- | :--- | :--- |
| **Skeptic** | Find flaws and contradictions | "Find every flaw in this reasoning. Be ruthlessly critical. Challenge every assumption." |
| **Expert** | Ensure technical accuracy | "Verify this against formal technical standards. Focus on accuracy and precision." |
| **Adversary** | Attempt logical invalidation | "Try to logically invalidate this claim. Act as the devil's advocate." |
| **Archivist** | Anchor in evidence | "Anchor this in the retrieved evidence. Point out any gaps in the provenance." |
| **Generalist** | Synthesize balanced view | "Provide a balanced synthesis of the facts." |

Each lens is spawned in isolation—it does not see the output of the other lenses. This isolation is architecturally critical. If the lenses could communicate, they could converge on a shared hallucination through social dynamics. Isolation ensures that convergence can only occur through agreement on the underlying evidence, not through mutual influence.

### 3.4 The Consensus Gate: $N$-of-$M$ Rule

Once all $M$ lenses have completed their analysis, Janus applies the **Deterministic Consensus Gate**. This is not a "voting" mechanism where the model decides who won. It is a structural rule implemented in code:

**The $N$-of-$M$ Rule:** An output is emitted **if and only if** $N$ lenses (typically $N \ge 3$ for $M = 5$) achieve exact consensus on the core factual claim.

#### 3.4.1 The Agreement Calculation

The agreement calculation is deterministic, not LLM-judged. A specialized Judge function cross-references the lens outputs for factual alignment:

1. Each lens output is decomposed into atomic claims.
2. Claims are compared across lenses for identity (same fact with same confidence).
3. Consensus count is calculated as the number of lenses that agree on the most-supported claim.

This is implemented as code in `infra/api/src/core/orchestrator.py`. The model is not asked to "judge" the outcome—it is asked to produce outputs that are then algorithmically compared. This separation of Generator and Auditor is the architectural guarantee that the consensus math cannot be faked.

#### 3.4.2 The Precision-Recall Tradeoff

The $N$ threshold represents a deliberate trade-off:

| $N$ (for $M=5$) | Behavior | Precision | Recall |
| :--- | :--- | :--- | :--- |
| $N=5$ | All lenses must agree | Maximum precision, minimal recall | System answers fewer questions but is never wrong |
| $N=4$ | All lenses agree or one dissents | High precision | Moderate recall |
| $N=3$ (default) | Simple majority required | Good precision | Good recall |
| $N=2$ | Loose agreement | Lower precision | Higher recall, risk of false positives |

The default $N=3$ is calibrated to the $\tau$ threshold: when Soter has already flagged a query as high-risk ($T=1$), requiring a supermajority of lenses to agree provides a strong secondary verification layer. If consensus fails at $N=3$, the system returns `[Sovereign Unknown]` rather than emitting a contested claim.

### 3.5 The Sovereign Seal

Every output from SOL mode carries a **Sovereign Seal**—an epistemic label generated by code that tells the user exactly how much certainty is behind the answer:

| Seal | Meaning | Conditions |
| :--- | :--- | :--- |
| `[Sovereign Consensus: 5/5]` | Absolute Certainty | All 5 lenses agreed on the core claim |
| `[Sovereign Consensus: 4/5]` | High Confidence | 4 of 5 lenses agreed, one dissented |
| `[Sovereign Consensus: 3/5]` | Verified | Consensus threshold met, but with internal divergence |
| `[Sovereign Unknown]` | Epistemic Failure | Consensus not reached, or τ tripwire triggered before consensus |

The seal is not a suggestion. It is a mandatory prefix on every SOL output. The user does not need to trust the model's self-assessment of its own confidence—the seal is generated by the deterministic layer and cannot be modified by the probabilistic engine.

#### 3.5.1 The Sovereign Receipt

Alongside the seal, the system can produce a **Sovereign Receipt**—a human-readable traversal of the cognitive chain that enables any auditor to verify the reasoning path (see Vol II §2.3.3). The receipt traces the output from the user's query, through Soter's risk assessment, through Mnemosyne's grounding, through Janus's lens consensus, to the final seal.

A researcher with access to the ArangoDB instance can independently verify that:
1. The Genesis Block at the root of the chain has not been tampered with.
2. Every intermediate block's hash matches its predecessor.
3. The consensus count on the seal matches the actual lens outputs stored in the events collection.

This is the final accountability layer: **truth claims are not just asserted; they are backed by a cryptographically verifiable audit trail.**

### 3.6 The Orchestration Flow

The complete orchestration flow through Janus:

```
User Query
    ↓
Soter Risk Scan (τ = 0.15 tripwire)
    ├── Low Risk → NOX Mode (probabilistic generation)
    └── High Risk (T=1) → Mode Switch → SOL Mode
                                    ↓
                            Mnemosyne Grounding
                            (fragment retrieval with Divine Priority)
                                    ↓
                            Sovereign Spawning (M=5 lenses)
                            ↓            ↓         ↓         ↓         ↓
                        [Skeptic]  [Expert]  [Adversary]  [Archivist]  [Generalist]
                            ↓            ↓         ↓         ↓         ↓
                            Deterministic Consensus Gate (N≥3)
                                    ↓
                            Soter Veto Gate (final risk check)
                                    ↓
                            Output with Sovereign Seal
                            [Sovereign Consensus: X/5]
                                    ↓
                            Sovereign-Nexus Hash Chain (immutable record)
```

Every arrow in this flow is enforced by code, not by prompt instructions. The model cannot skip a step, cannot influence the consensus calculation, and cannot modify the seal. The orchestration layer is a pipeline, not a conversation.

### 3.7 Integration with the Sovereign Architecture

Janus is not a standalone system. It integrates with the two other architectural components:

- **Soter Integration:** Janus receives the $T$ signal from Soter and executes the mode switch. If Soter blocks an output at the final veto gate, Janus does not attempt to rephrase or "try again"—it returns `[Sovereign Unknown]`.
- **Nexus Integration:** Every lens output, every consensus calculation, and every seal is recorded as a `CognitiveBlock` in the Sovereign-Nexus chain. The orchestration logic itself becomes part of the immutable record.
- **Anchor Integration:** During Mnemosyne grounding, Divine Priority retrieval ensures that Genesis Blocks surface in each lens's context window. The lenses all see the same anchors, ensuring that human truths are propagated consistently.

The result is a fully integrated cognitive pipeline where every claim is sensed, grounded, debated, verified, sealed, and recorded. No step relies on the model's "good behavior." Every step is a deterministic function of the system's architecture.
